# BD-001.16 - Slice K Structured Observability Discovery

**Status:** DISCOVERY COMPLETE - implementation planning authorized

**Purpose:** reconcile the frozen Slice K observability boundary against the
current structlog configuration, sanitizer, reliability logging, audit path,
and document/biometric/liveness processors.

This record introduces no new architecture and does not reopen the closed
Slices G, G.2, H, I, or J.

## 1. Governing boundary

Slice K adds structured operational observability for the verification
pipeline while preserving the separation between:

```text
Audit event
    durable/security-relevant business record

Structured application log
    operational observability

EvidenceResult
    verification-domain state
```

Logs must observe execution and dependency behavior. They must not make
verification decisions, persist evidence, replace audit events, or become a
source of policy semantics.

The following must never be logged as payloads or raw values:

- document images or raw document content;
- selfie bytes, cropped face images, or liveness frames;
- embeddings, biometric templates, or similarity inputs;
- OCR raw text;
- NIN, BVN, or other identity numbers;
- sensitive provider responses;
- credentials, tokens, or secrets.

## 2. Current implementation facts

### 2.1 Structured logging configuration

`infrastructure/observability/logging.py` configures structlog at application
startup with:

- log-level filtering from `Settings.log_level`;
- log level and ISO timestamp processors;
- `core.security.classification.sanitize_metadata` applied to every event;
- JSON rendering to stdout.

This is the correct shared foundation for Slice K. No new logging framework or
sink is required.

### 2.2 Existing structured events

`infrastructure/observability/reliability_logging.py` is the only dedicated
structured event producer found in the current observability package. It emits:

- `dependency_call` for guarded dependency operations;
- `reliability_metrics` for periodic aggregate snapshots.

These events intentionally carry operational fields such as dependency,
operation, outcome, attempts, duration, reason code, request ID, and optionally
session ID. They do not carry tenant IDs, content, credentials, or biometric
payloads.

The reliability event shape is a useful local precedent, not a new generic
pipeline abstraction to introduce prematurely.

### 2.3 Sanitization behavior

The sanitizer recursively bounds mappings/sequences and redacts known sensitive
and highly sensitive field names, binary values, oversized strings, cycles, and
unserializable values. Known protected names include authorization, document,
image, selfie, liveness, embedding, biometric template, tokens, secrets, NIN,
and BVN.

Operational identifiers such as request ID, correlation ID, session ID, event
name, stage name, outcome, duration, provider name, and model ID remain usable
when passed under non-sensitive field names. `tenant_id` is not currently
classified as sensitive by the sanitizer, so logging tenant context requires a
separate governance decision rather than assuming the sanitizer makes it safe.

Sanitization is a defense-in-depth boundary, not permission to pass arbitrary
payload dictionaries to a logger. Stage log call sites must construct
allow-listed operational fields explicitly.

### 2.4 Context propagation

The current code passes request ID and correlation ID explicitly through API,
workflow, document, and biometric method signatures where available. There is
no discovered shared structlog context-variable binding that automatically
injects request ID, correlation ID, session ID, or tenant ID into every event.

Reliability logging accepts request ID and session ID explicitly and deliberately
omits tenant ID. Slice K must decide whether to retain explicit fields at stage
call sites or add a narrowly scoped context-binding mechanism. It must not
silently add tenant identity to every log event.

### 2.5 Existing stage behavior

`SqlAlchemyDocumentProcessor` and `BiometricProcessor` persist stage evidence
and use audit services, but do not currently emit dedicated structured stage
completion/failure events. Their evidence rows and audit events are not
operational logs and must not be replaced by logs.

`InsightFaceLivenessProvider` computes the Temporal Liveness Demo heuristic and
has no structured stage logging. Slice J captures frames but does not invoke
this provider; Slice K must preserve that boundary.

The API and workflow layers already have request/session information available,
but no uniform stage-event vocabulary has been frozen in code.

### 2.6 Audit boundary

`AuditService.record()` creates durable, required or best-effort audit events
and sanitizes audit metadata. Audit ordering and durability are business and
security semantics. A log line cannot satisfy a required audit event, and an
audit event must not be used as a high-volume timing or debug log.

## 3. Reconciliation decisions needed by the implementation plan

These are implementation-plan decisions, not a reopening of the observability
architecture:

1. **Event vocabulary:** freeze stable event names such as
   `verification_stage_started`, `verification_stage_completed`,
   `verification_stage_inconclusive`, `verification_stage_unavailable`, and
   `verification_stage_failed`, or choose an equivalent bounded vocabulary.
2. **Stage identity:** use an allow-listed `stage` value covering document
   quality/classification/MRZ/barcode/OCR/field extraction, reference
   acquisition, face detection/quality/embedding/match, and the Temporal
   Liveness Demo where it is actually invoked.
3. **Required fields:** freeze only operational fields such as stage, outcome,
   duration, request ID, correlation ID, session ID, evidence-result ID, model
   ID/version, retry attempt, and failure category. Do not log result payloads.
4. **Context policy:** decide whether tenant ID remains excluded, hashed, or is
   included only under an explicit sensitive-data policy. Do not infer safety
   from the current sanitizer.
5. **Emission location:** stage owners should emit stage events at the
   orchestration boundary, not low-level model adapters, so provider internals
   cannot multiply events under retries or concurrent calls.
6. **Retries/concurrency:** each actual stage attempt may emit a bounded event
   with an attempt number; events must not mutate evidence or decision state and
   duplicate logs must remain operationally tolerable.
7. **Failure taxonomy:** distinguish `INCONCLUSIVE`, `UNAVAILABLE`, timeout,
   and unexpected exception in logs without mapping operational failure into a
   verification verdict.
8. **Exception safety:** log a sanitized operational failure category and
   correlation identifiers, then re-raise according to the existing processor
   and workflow contracts. Logging failure must not shadow the original failure.
9. **Payload-leak tests:** prove sanitizer behavior with canary values and
   inspect representative stage events for absence of raw bytes, OCR text,
   embeddings, identity numbers, and provider payloads.

## 4. Proposed validation surface

The implementation plan must include focused tests for:

- JSON event shape and stable event names;
- stage success, inconclusive, unavailable, timeout, and exception events;
- request/correlation/session context propagation;
- retry attempt and duration fields;
- concurrent processing producing no decision or evidence mutation through
  logging;
- raw bytes, embeddings, OCR text, NIN/BVN values, and liveness frames never
  appearing in rendered logs;
- required audit events remaining durable independently of logs;
- logger failure not masking the underlying processor/provider exception;
- existing reliability events retaining their current fields and behavior.

## 5. Findings

- The repository already has the correct structlog JSON and sanitizer base.
- Structured reliability events exist, but pipeline-stage observability is not
  consistently emitted.
- Audit events and evidence results are separate mechanisms and must remain so.
- Current explicit request/correlation propagation is usable, but there is no
  automatic global context binding to assume or silently introduce.
- Tenant identifiers require an explicit logging decision; current sanitizer
  classification does not automatically redact `tenant_id`.
- Slice K must not invoke or activate the Temporal Liveness Demo provider as a
  side effect of adding observability.

## 6. Decision and next step

**Decision:** Slice K discovery is complete. The existing logging foundation is
sufficient; the missing work is a bounded stage-event vocabulary, safe field
allow-list, context policy, emission placement, and hostile log-leak tests.

**Next step:** write `BD-001.17` as the frozen Slice K implementation plan.
No production code is changed by this record.
