## 3. Liveness rows — why "inapplicable," not "deferred coverage"

Confirmed directly against the code, not inferred: `grep` across
`infrastructure/face/processor.py`, `core/verification/workflow.py`, and
`apps/api/paxli_api/dependencies.py` for `LivenessAssessor`/
`LivenessProvider` returns zero matches. `BiometricProcessor.__init__` has
no liveness parameter at all (see `BD-001.21` §3 for the full comparison
against the master plan's original sketch).

A hostile test for "single-frame protocol violation" or "replay" against
the liveness *assessment* step has nothing to attack: no code path ever
calls `LivenessProvider.assess()` outside its own unit tests
(`test_insightface_liveness_provider.py`), and no `LIVENESS_ASSESSMENT`
evidence row is ever produced by the running system. The coverage that
*does* exist and *is* correct for what is actually active today:

- **Capability level** (`test_insightface_liveness_provider.py`): rejects
  0/1 frames as insufficient, rejects undecodable/no-face/ambiguous
  frames, reports zero score for zero movement (the capability-level
  equivalent of a replay input), clamps large movement, raises on
  degenerate/non-finite landmarks.
- **Capture-boundary level** (`test_evidence_media_validation.py`):
  bounds `/liveness` to 1–5 frames, rejects 6+ before persistence,
  per-frame idempotency, partial-failure-stops-before-next-frame, and
  confirms the capture route itself never invokes the provider.

This matches `BD-001.16`/`BD-001.18`'s own explicit, repeated statement of
the same boundary. Marking these two rows "covered" would be dishonest;
marking them a coverage gap this record failed to close would misrepresent
what's actually being protected against today. **"Inapplicable pending
activation"** is the accurate status. Re-open both rows the day a future
slice wires liveness assessment into `BiometricProcessor` — that slice
inherits this exact matrix row, not a fresh one.

### 4.1 The event-loop harness issue — tracked, not closed, not a product defect

Running `tests/unit` + `tests/integration` + `tests/contracts` +
`tests/security` **together in one pytest process** fails one pre-existing,
unrelated test (`test_reference_not_available_persists_nothing`) with
`RuntimeError: Event loop is closed`, deep inside `asyncpg`, on the very
first `session.flush()` call in the module. Reproduced twice under that
exact combined condition. Isolated by running `tests/integration` +
`tests/contracts` + `tests/security` **without** `tests/unit` in the same
process — clean, twice, including with both new tests present. The
mechanism: multiple integration test files each dispose a shared,
module-level SQLAlchemy engine singleton
(`infrastructure/database/session.py`) in their own `autouse`,
module-scoped teardown fixture; when `tests/unit`'s many additional test
modules share the same pytest session and event-loop-per-module boundaries
with the integration suite, a disposed pool from one module's teardown can
be reused by a connection object still bound to a different module's
(closed) event loop.

This is a genuine, pre-existing test-infrastructure fragility — not
introduced by this session's two new tests (confirmed by the isolated
re-run above), not a `BiometricProcessor` defect, and not a Decision Engine
or evidence-integrity defect. It is **recorded here as an open, tracked
follow-up**, not folded into a "full suite: clean" claim for every possible
execution mode. The safe, currently-used validation path — `tests/unit`
alone, and `tests/integration`+`tests/contracts`+`tests/security` alone —
is unaffected and is what this and the preceding remediation record actually
rely on.
