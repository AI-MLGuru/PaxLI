## 1. `ReferenceIdentity` — full specification

BP-001 §6d froze the principle (`FaceMatcher` must never know a
reference's source) but only sketched the shape. Resolving the fields:

> **BP Decision 18 — `ReferenceIdentity` shape.** `ReferenceIdentity` is
> a transient domain value assembled by the orchestrator (§5) — **not**
> a new persisted `EvidenceResultType` and **not** a new evidence-result
> row. This mirrors the existing precedent exactly:
> `DocumentFieldReconciler.reconcile()` (`core/document/reconciliation.py:44`)
> receives `OCRExtraction | None`, `MRZExtraction | None`,
> `BarcodeExtraction | None` — domain values the orchestrator assembles
> from already-persisted `EvidenceResult` rows, not new rows themselves.
> `ReferenceIdentity` plays the same role for the reference side of a
> `FaceMatch` computation.
>
> ```python
> class ReferenceProvenance:
>     acquisition_route: Literal[
>         "DOCUMENT_BOUND", "NIN_DATA_PRINT_BOUND", "EXTERNAL_PROVIDER_BOUND"
>     ]  # (A) / (A') / (B) per BP-001 §6b — never "SESSION_INTERNAL" (C),
>        # which BP Decision 6 already rejects as unconstructable here
>     source_evidence_result_ids: tuple[UUID, ...]  # what established
>         # the identity claim — e.g. a DOCUMENT_FIELD_EXTRACTION row's id
>
> class ReferenceArtifact:  # tagged union, not a single shape
>     # Image variant: a face region still needing FaceDetector /
>     # FaceQualityAssessor / FaceEmbedder — (A) and (A') when the
>     # provider/document returns a photograph
>     # Embedding variant: an already-computed embedding — (B) shape (i)
>     # when a provider returns a template directly, per BP-001 §6c's
>     # own research-brief row "does it return a biometric
>     # template/embedding directly?"
>
> class ReferenceIdentity:
>     identity_claim: <pointer to whatever established WHO this
>         reference asserts to be — not duplicated data, a reference>
>     reference_artifact: ReferenceArtifact
>     provenance: ReferenceProvenance
> ```

**Why the tagged union matters, concretely:** if `reference_artifact` is
an `Image`, the orchestrator must run `FaceDetector` →
`FaceQualityAssessor` → `FaceEmbedder` on it before a comparison is
possible. If it's already an `Embedding` (a provider template, §6c
shape (i)'s embedding sub-case), those three stages are skipped
entirely for that side — there is no image to detect a face in. Without
this union, the orchestrator (§5) would have no principled way to know
which stages apply to the reference side, and would end up
special-casing acquisition routes exactly where BP Decision 13 forbids
it (`FaceMatcher`/the orchestrator "must not know... whether a
representation... came from a document scan, a NIN Data Print, an
external provider"). The union is scoped to *shape* (image vs.
embedding), never to *source* — preserving that boundary.

Exact module path/class implementation (dataclass vs. Pydantic model,
file location) is `BP-002` territory, mirroring BP-001 §7's own
"exact name/location is implementation-plan territory" carve-out for
`FaceMatcher`.

## 2. `FaceEmbedding` — full specification, and two compatibility checks that must not be conflated

`FaceEmbeddingResult` (`core/evidence_result/schemas.py:25-27`) is
confirmed unchanged from BP-001 §4's citation:

```python
class FaceEmbeddingResult(BaseModel):
    embedding: tuple[float, ...]
    embedding_dimensions: int
```

Model identity (`model_id`, `model_version`) is **not** duplicated
inside this payload — it already lives on the wrapping
`EvidenceResult.model_reference: ModelReference | None`
(`core/evidence_result/models.py:52`), the same field every prior phase
used. No schema change is needed here; the existing field carries
exactly what compatibility checking needs.

**The important finding: there are two distinct compatibility checks,
already partially built, and BP-001 §7a's "mechanism OPEN" note
conflated them.** Verified directly in `core/decision/evaluator.py:169-214`:

> **BP Decision 19 — Two compatibility checks, two layers, refining BP
> Decision 7.**
>
> 1. **Decision-Engine-level (ALREADY BUILT, confirmed live):**
>    `_check_calibration_compatibility` checks whether a `FACE_MATCH`
>    evidence row's own `model_reference` matches the *threshold
>    definition's* `model_id`/`model_version` before a policy applies
>    that threshold to it — `CALIBRATION_MODEL_MISMATCH` otherwise. This
>    governs "is this threshold safe to apply to this evidence." It says
>    nothing about whether the comparison itself was computed
>    correctly, and requires zero new code for biometrics (BP Decision
>    11 already established this, now confirmed at the FaceMatch-specific
>    level too).
> 2. **`FaceMatcher`-level (NOT YET BUILT — this is BP Decision 7's
>    actual subject):** before computing similarity, are the
>    *reference* embedding's `model_reference` and the *probe*
>    embedding's `model_reference` identical to each other? If not, the
>    resulting similarity score is meaningless (comparing incompatible
>    vector spaces) regardless of what the eventual `FACE_MATCH` row's
>    own `model_reference` later says.
>
> Resolving (1) does not resolve (2) — they check different pairs of
> things (evidence-vs-threshold vs. reference-vs-probe) at different
> times (policy evaluation vs. comparison time). BP Decision 7's
> "mechanism OPEN" note is narrowed to (2) only; (1) requires no further
> decision.

**Where (2) belongs, resolved now:** inside `FaceMatcher.compare()`
itself, not a separate upstream compatibility registry or the
orchestrator. `compare()` is the only point that structurally receives
both representations at once (BP Decision 8); pushing the check upstream
would duplicate knowledge of what "compatible" means outside
`FaceMatcher`'s own boundary, and — per BP Decision 13 — the
orchestrator is not supposed to reason about embedding internals at
all. What `compare()` does on a mismatch (raise, or return a specific
`FaceMatchResult`/status value) is resolved in §3 below, not here.

## 3. `FaceMatch` — full contract

Current schema (`core/evidence_result/schemas.py:30-31`), confirmed:

```python
class FaceMatchResult(BaseModel):
    similarity: float
```

Two concrete gaps, both resolvable without any provider knowledge:

### 3a. Reference/probe lineage needs explicit roles, not positional convention

`FaceMatch` is the first evidence type in this project with **two
parents of the identical `EvidenceResultType`** (`FACE_EMBEDDING`,
`FACE_EMBEDDING`) — `parent_evidence_result_ids` alone cannot
distinguish "which one was the reference" from "which one was the
probe" by type, the way `DOCUMENT_FIELD_EXTRACTION`'s three
differently-typed parents (OCR/MRZ/Barcode) could. A purely positional
convention (index 0 = reference, index 1 = probe) is exactly the kind
of implicit convention this project's own precedent argues against
(`Gate.kind` being an explicit field rather than inferred, DE-003 §4;
`ThresholdDefinition`'s explicit fields replacing "the previous bare
`dict[str, float]`," `core/policy/thresholds.py:1-5`).

> **BP Decision 20 — `FaceMatch` role disambiguation.** `FaceMatchResult`
> carries explicit `reference_evidence_result_id: UUID` and
> `probe_evidence_result_id: UUID` fields in its own payload, in
> addition to both ids appearing in the wrapping `EvidenceResult`'s
> `parent_evidence_result_ids` (so the existing generic freshness
> machinery, BP Decision 10, keeps working completely unchanged — it
> only needs the *collection* of parents, not their roles; the
> implementation happens to preserve tuple order, but generic consumers
> MUST NOT interpret that order as reference/probe semantics — only the
> two named payload fields carry role meaning). The payload fields are
> what let a reader (a policy author, an auditor, a future
> `FaceIdentifier`) recover *which side was which* without relying on
> positional convention.
>
> **Domain invariant, enforced at construction (mirroring
> `FieldReconciliationResult.__post_init__`'s own enforced-invariant
> precedent, `core/document/types.py`):**
>
> ```text
> reference_evidence_result_id ∈ parent_evidence_result_ids
> probe_evidence_result_id ∈ parent_evidence_result_ids
> reference_evidence_result_id != probe_evidence_result_id
> ```
>
> Without this, the payload could claim `reference=A, probe=A,
> parents=(A, B)` and the generic provenance machinery would raise
> nothing — `_validate_provenance` only checks that every parent belongs
> to this tenant/session, never that the role fields are consistent with
> the parent set. The invariant closes exactly that gap; it is a domain
> rule belonging to `FaceMatchResult` itself, not a change to any
> generic mechanism.

**Resolving "domain result, envelope, or both" explicitly — this was
raised as still-open and is answered here, not left ambiguous:** both,
deliberately, because the two fields serve two structurally different
consumers that must not be conflated into one. `parent_evidence_result_ids`
is read by generic, evidence-type-agnostic machinery (BP Decision 10's
freshness check, `_validate_provenance`'s tenant/session enforcement) —
that machinery must stay ignorant of what a "reference" or "probe" even
means, the same way it's ignorant of what an "OCR result" means.
`reference_evidence_result_id`/`probe_evidence_result_id` are read by
`FACE_MATCH`-specific consumers (a policy author, an auditor, a future
`FaceIdentifier` comparing candidates) that need the role, not just the
set. This is the same split already proven for
`DOCUMENT_FIELD_EXTRACTION`: `parent_evidence_result_ids` carries the
generic parent collection, while `conflicted_fields` (DP-001 Addendum A)
carries type-specific detail inside the payload — nothing new is being
invented here, only the established pattern applied to a case with two
same-typed parents instead of three differently-typed ones. Duplication
between the two fields is intentional, not an oversight: removing
either one would break one of the two consumers.

```python
class FaceMatchResult(BaseModel):
    similarity: float
    reference_evidence_result_id: UUID
    probe_evidence_result_id: UUID
```

### 3b. Status semantics — comparison success, not a match verdict

`EvidenceResultStatus`'s closed vocabulary
(`core/evidence_result/enums.py:13-18`) is
`NOT_REQUIRED/NOT_SUBMITTED/UNAVAILABLE/INCONCLUSIVE/PASS/FAIL`.
DEC-5.14's own worked example (`FaceMatch.similarity >= calibrated_threshold`,
cited in BP-001 §3) evaluates similarity **as a policy condition** — it
does not describe `FaceMatch` itself deciding match/no-match. That is
the same "evidence is not a verdict" boundary this project enforces
everywhere else, made concrete for this evidence type:

> **BP Decision 21 — `FaceMatch` status semantics.** `status=PASS` means
> a similarity score was successfully computed between two *compatible*
> representations — regardless of whether that score is high or low. A
> low similarity is still a successful, valid comparison, carried
> honestly in `similarity`; `FaceMatch` does not threshold its own
> output.
>
> **FROZEN principle, separated deliberately from its implementation
> mapping:** an incompatible reference/probe pairing (§2's `BP Decision
> 19` point 2) MUST NEVER produce a similarity score — no number is
> silently computed from vectors that cannot be meaningfully compared.
> This is the "technical failure is not identity failure" principle
> (`CLAUDE.md`), applied here.
>
> **NOT frozen here, left explicitly to `BP-002`:** which exact
> `EvidenceResultStatus` value (and reason code) represents that
> refusal. The first draft of this decision mapped it to `UNAVAILABLE`
> alongside ordinary capability/model failure — that conflates two
> different things that happen to share a status value today: a
> *technical* inability to run the comparison at all (the operation
> itself is broken) versus the comparison operation running correctly
> and correctly refusing *invalid input* (two representations that were
> never comparable to begin with — the system is not unavailable, it
> received an incompatible pairing). Collapsing these prematurely
> repeats a mistake this project already corrected once in Document
> Processing: don't merge distinct failure semantics just because the
> current status vocabulary has limited members. The exact mapping may
> matter for reason codes, observability, retryability, and operator
> diagnosis in ways this discovery-level document has no basis to
> settle — `BP-002` resolves it, informed by whatever `FaceMatcher`'s
> actual implementation needs.
>
> Whether `FaceMatch` ever has a genuine capability-level `FAIL`
> (structurally analogous to MRZ's check-digit mismatch) is similarly
> **not established** — no analogous self-consistency check exists for a
> similarity computation the way a checksum exists for MRZ, so this
> stays an explicitly OPEN question rather than a forced answer (§7).

Threshold/calibration binding needs no new field here — `ThresholdDefinition.applicable_evidence_type: str`
(`core/policy/thresholds.py:18`) is a generic string, not a hardcoded
enum, already confirmed reusable for any `evidence_type` including
`FACE_MATCH` with zero engine change (BP Decision 11, now confirmed at
the field level rather than only asserted).

## 4. Biometric evidence lineage, in concrete `parent_evidence_result_ids` terms

BP-001 §11 froze the freshness *principle* (BP Decision 10). Resolving
what the actual lineage graph looks like, per acquisition route:

```text
(A) Document-bound:
  DOCUMENT_FIELD_EXTRACTION ──┐
  [new face-extraction        ├──► FACE_DETECTION(ref) ──► FACE_QUALITY(ref) ──► FACE_EMBEDDING(ref)
   capability, BP Decision 15]┘                                                          │
                                                                                          │
  SELFIE capture ──► FACE_DETECTION(probe) ──► FACE_QUALITY(probe) ──► FACE_EMBEDDING(probe)
                                                                                          │
                              FACE_EMBEDDING(ref) ──┬────────────────────────────────────┘
                                                     ▼
                                                FACE_MATCH
                                     parent_evidence_result_ids = (ref.id, probe.id)
                                     reference_evidence_result_id = ref.id
                                     probe_evidence_result_id = probe.id

(A') NIN Data Print-bound:
  [NIN-lookup provider result] ──► FACE_DETECTION(ref) ──► FACE_QUALITY(ref) ──► FACE_EMBEDDING(ref)
  (same shape from here on as (A) — this is exactly what BP Decision 13
   is for: the graph is identical downstream of acquisition)
```

Each stage's own `parent_evidence_result_ids` uses the same
exact-identity freshness rule already hostile-validated for
`DOCUMENT_FIELD_EXTRACTION` (DP-008 §4, HV-013) — nothing new to
design, only to apply: `FACE_DETECTION(ref)`'s parent is whatever
produced the reference image; `FACE_QUALITY(ref)`/`FACE_EMBEDDING(ref)`
chain from there; `FACE_MATCH`'s parents are the two `FACE_EMBEDDING`
rows, disambiguated per §3a.

**One asymmetry worth naming explicitly, not glossing over:** the
probe-side sub-chain (`FACE_DETECTION(probe)` →
`FACE_QUALITY(probe)` → `FACE_EMBEDDING(probe)`) is structurally
identical to the reference-side sub-chain regardless of acquisition
route (A)/(A') — the *route* only changes what feeds the *reference*
side. This confirms BP Decision 13's abstraction actually holds at the
lineage-graph level, not just as a stated principle: swapping (A) for
(A') changes exactly one edge in this graph (what feeds
`FACE_DETECTION(ref)`), nothing downstream of it.

## 5. Cross-capture orchestration — challenged and re-derived, not merely asserted

BP-001 §8/BP Decision 9 froze that `SqlAlchemyDocumentProcessor`'s exact
shape does not transfer, without proposing what does. The first draft
of this section asserted "eager, event-triggered" as a conclusion; per
your challenge, that's a new architectural decision and needs to be
argued from the candidate space, not stated as the obvious consequence
of the "Decision Engine never triggers production" observation.

### 5a. Four candidate models, evaluated

| Model | Shape | Verdict |
|---|---|---|
| **A. Eager, inline** | Each capture-side stage completion, handled synchronously within the same request/transaction that produced it, checks the other side and attempts `FaceMatch` if ready | **Adopted** — see below |
| **B. Decoupled event bus** | A produced-`FACE_EMBEDDING` domain event is published; a separate async consumer reacts, decoupled from the originating request | **Rejected for V1** — requires a message bus/event infrastructure this codebase does not have and CLAUDE.md's own dependency discipline explicitly bars adding "merely because conventional" ("Do not add Redis, Kafka... queues... merely because they are conventional... establish that it is required by the specification and that existing dependencies cannot satisfy the need"). Nothing below requires it. The adopted model (D) is deliberately never described as "event-triggered" elsewhere in this section, to avoid it being misread as this option. |
| **C. Explicit stateful workflow** | A new persisted "biometric verification workflow" state machine (`WAITING_FOR_REFERENCE`, `WAITING_FOR_PROBE`, `BOTH_READY`, `MATCHED`, ...) | **Rejected for V1** — introduces a new state dimension. CLAUDE.md's State Separation principle already enumerates the dimensions this project maintains (session lifecycle / processing execution / evidence status / final decision); a persisted biometric-workflow state would need to be justified as fitting one of those or as a deliberate new one, and §5b below shows every scenario is resolvable by *querying* existing effective-evidence state, not by *persisting new* state — so the complexity has no offsetting benefit |
| **D. Hybrid (A, hardened)** | Model A, with explicit invariants for concurrency, idempotency, and staleness rather than assuming they fall out for free | **This is what "adopted" actually means below** — not bare A, A with its edges checked |

> **BP Decision 22 — Orchestration trigger model (revised).** Biometric
> orchestration is **eager, inline, and symmetric: completion of either
> the reference-side or the probe-side evidence pipeline may trigger a
> `FaceMatch` attempt** (model A/D) — explicitly **not** a decoupled
> event bus (B), and **not** a new persisted biometric workflow state
> machine (C). `FaceMatch` is produced only once both effective
> embeddings are available. ("Event-triggered" is deliberately avoided
> as a label for this — it invites confusion with option B, which this
> decision rejects; "completion-triggered" is used instead.) Two
> independent entry points:
>
> - **Reference-side trigger:** fires whenever the upstream evidence
>   that would populate a `ReferenceIdentity` becomes available. Runs
>   `FaceDetector` → `FaceQualityAssessor` → `FaceEmbedder` on the
>   reference artifact, reusing `_is_reusable`/`_persist_stage`
>   (`infrastructure/document/processor.py:136,339`).
> - **Probe-side trigger:** fires whenever a `SELFIE` capture is
>   submitted. Runs the identical three-stage sub-pipeline on the probe.
> - **`FaceMatch` attempt:** triggered by *either* side's `FACE_EMBEDDING`
>   stage completing, checking whether the other side already has a
>   usable effective `FACE_EMBEDDING`. **No `FACE_MATCH` row is created
>   until both sides are ready** — there is no placeholder/"waiting"
>   row and no new status value for this; absence of an effective
>   `FACE_MATCH` row *is* the "not yet" signal, exactly as the absence
>   of any `OCR_EXTRACTION` row before `DocumentProcessor` first runs is
>   never itself a row. If a Decision Engine evaluation happens before
>   both sides are ready, the existing, unmodified
>   `_check_required_evidence` path already produces
>   `INCONCLUSIVE`/`REQUIRED_EVIDENCE_MISSING` — zero new code, per
>   BP Decision 11.

**Why not lazy-at-evaluation-time (a fifth option, ruled out
first):** Decision Engine evaluation has never triggered evidence
production in this codebase — `list_effective_for_session`
(`core/evidence_result/service.py:425`) is read-only. Making
`FaceMatch` production happen lazily at evaluation time would be a
first-of-its-kind inversion of that boundary. This rules out laziness;
it does not, by itself, prove eager-*and*-decoupled (B) or
eager-*and*-stateful (C) are wrong — §5b does that work directly
against your scenario list.

### 5b. Hostile scenario pass

Every scenario resolves using **already-existing, generic mechanisms**
confirmed by direct code inspection (§6) — none required inventing
anything beyond what §1-§4 already specify. Where a scenario exposes a
genuine gap, it's marked OPEN rather than forced.

| Scenario | Resolution | Mechanism |
|---|---|---|
| Reference arrives first | No `FACE_MATCH` row yet; probe-side trigger will complete the attempt later | "No row until both ready" (above) |
| Probe arrives first | Symmetric | Same |
| Reference retry supersedes embedding | Reference-side trigger re-fires on the new effective `FACE_EMBEDDING(ref)`; if a `FACE_MATCH` already exists, its parent set no longer matches → stale per BP Decision 10 → re-attempt calls `supersede()`, not `create()` | Exact-parent-identity freshness (DP-008 §4, HV-013), already generic |
| Probe retry supersedes embedding | Symmetric | Same |
| Both arrive concurrently | Two near-simultaneous `create()` calls for the same `(tenant_id, session_id, FACE_MATCH)` — **already handled**: the loser hits `EffectiveResultAlreadyExistsError` and returns the winner's row instead of erroring (`core/evidence_result/service.py:223-245`, proven live for other evidence types in HV-010) | Existing unique-index race handling, fully generic — confirmed by re-reading `create()` directly, not assumed |
| Same embedding submitted twice (duplicate capture) | Resolves to the same row via `idempotency_key`, provided the capture-side trigger threads a stable key (e.g. derived from the `Evidence` capture's own id) | Existing `idempotency_key` mechanism (`create()`'s own param) — the *mechanism* is confirmed available; threading a stable key through is `BP-002` wiring |
| Different model versions (ref v1, probe v2) | `FaceMatcher.compare()` detects `model_reference` mismatch, refuses to compute a score (exact status/reason-code left to `BP-002`, per Decision 21's revised split) | BP Decision 19 point 2 / BP Decision 21 |
| Same dimensions, different models | Explicitly why BP Decision 19 checks `model_id`+`model_version`, never dimensionality alone (BP-001 §7a's own original framing) | Same |
| Provider unavailable | Reference-side trigger never produces a usable reference; for NIN specifically, BP-001 §6f/BP Decision 16's Document-Intelligence fallback applies; either way, no `FACE_MATCH` row is fabricated | "No row until both ready" + BP Decision 16 (provider-dependent fallback itself stays out of scope here, per §7) |
| Reference unavailable (e.g. face-extraction capability fails on a document) | Capability-level `UNAVAILABLE` on the reference sub-chain; no usable `FACE_EMBEDDING(ref)`; same as above | Same |
| Probe unavailable (no face detected in selfie, or embedder fails) | Symmetric | Same |
| `FaceMatch` recomputation | General form of the two supersession scenarios above | BP Decision 10 |
| Tenant crossing | A forged/cross-tenant `parent_evidence_result_id` is rejected before persistence — `_validate_provenance` checks every parent's `tenant_id`+`session_id` (`core/evidence_result/service.py:268-297`) | Existing, fully generic — confirmed by direct inspection, not assumed |
| Stale parent evidence | General form of the freshness scenarios above | BP Decision 10 |
| Partial pipeline completion | The `FaceMatch`-attempt trigger is scoped specifically to `FACE_EMBEDDING`-stage completion, not any earlier stage — a reference stuck at `FACE_DETECTION`/`FACE_QUALITY` simply never fires it | Trigger scoping (above) |

**One genuine gap the pass surfaced, correctly left OPEN rather than
answered here:** does a low `FACE_QUALITY` score *block* `FaceEmbedder`
from running at all, or does embedding always proceed and quality stays
purely informational for policy? This orchestration-sequencing question
depends directly on BP-001 §9.4/§9.5 (face cardinality and quality
structure), both already explicitly OPEN there — this pass did not
manufacture a premature answer just because orchestration touches it.
Whichever way §9.4/§9.5 eventually resolve, the trigger model above is
unaffected: it only cares whether `FACE_EMBEDDING` reached a reusable
effective status, not what gated it getting there.

**Net result:** model D (eager/inline, hardened) resolves all fifteen
scenarios using mechanisms already proven elsewhere in this codebase —
no new infrastructure, no new persisted state, no new concurrency
primitive. That's the argument for adopting it over B or C: not that
they're impossible, but that nothing in this scenario list demonstrates
a need for what they'd cost.
