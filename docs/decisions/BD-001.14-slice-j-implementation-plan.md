# BD-001.14 - Slice J Demo API Implementation Plan

**Status:** FROZEN - implementation authorized

**Purpose:** translates the frozen Slice J capture boundary and
`BD-001.13`'s repository reconciliation into exact router mechanics,
configuration, failure behavior, tests, and a hostile-validation gate.

No architectural decisions are introduced here. This plan does not reopen
BD-001, Slice F, Slice I, provider research, or the deferred liveness/PAD
boundary.

## 1. Scope

Slice J changes only the liveness capture surface:

- keep `/document` unchanged;
- keep `/selfie` unchanged;
- keep `/submit` unchanged;
- keep `GET /{session_id}/evidence` unchanged;
- change `/liveness` from one upload to a bounded collection of uploads.

The request parameter is:

```python
frames: Annotated[list[UploadFile], File(...)]
```

The accepted demo range is **1 through 5 frames**. A one-frame request is
accepted and produces a stored capture; the existing liveness provider's
`INSUFFICIENT_FRAMES` behavior remains a provider concern and is not silently
reimplemented in the capture route. A missing/empty multipart field is a
request-shape error. More than five files is rejected before any storage
mutation.

The endpoint remains explicitly a **Temporal Liveness Demo** / **Liveness
Heuristic Demo** surface. It must not claim production liveness or
presentation-attack detection.

## 2. Implementation boundary

| File | Change |
|---|---|
| `apps/api/paxli_api/routers/evidence.py` | change `/liveness` to accept and validate a bounded frame list; persist frames through the existing helper; preserve existing response and audit conventions |
| `apps/api/paxli_api/config.py` | add a settings value for the maximum liveness frame count, default `5`, with validation for a positive bounded value |
| `tests/unit/test_evidence_router.py` or the repository's existing evidence-router test module | add request-cardinality and per-frame validation coverage, using the established router dependency overrides |
| `tests/integration/test_evidence_submission.py` or the closest existing evidence API integration module | prove real persistence, idempotency, tenant/session enforcement, and evidence listing for a multi-frame submission |
| `docs/decisions/BD-001.15-slice-j-hostile-validation.md` | separate hostile-validation record after implementation, if the project keeps validation records per slice |

No changes are planned under `core/liveness/`, `infrastructure/liveness/`,
`core/verification/`, `core/decision/`, `core/face/`, or the workflow.

## 3. Persistence decision

Each accepted frame is persisted as its own `EvidenceType.LIVENESS` row/object
through the existing `EvidenceService.add()` path, in submission order.

This deliberately does not introduce a batch table, sequence aggregate, zip
format, video format, or new evidence abstraction. The existing storage and
retention/deletion lifecycle already knows how to protect and remove one
media capture at a time.

A multi-frame assessment result is **not** created by the capture endpoint.
The current `EvidenceResultService` provenance model supports one raw
`source_reference`, while a liveness batch has multiple raw `Evidence` IDs;
creating a synthetic batch result here would either lose provenance or require
a new batch abstraction outside Slice J. The existing `LivenessProvider` remains
available for a separately governed processing integration once that result
lineage boundary is designed.

The endpoint response remains the existing `EvidenceResponse` shape for the
last accepted frame, preserving backward compatibility for clients while the
full frame set remains retrievable through `GET /{session_id}/evidence`.

## 4. Frame processing algorithm

The route will use a dedicated multi-file helper adjacent to `store_upload()`
(or a small extension of that helper) with this sequence:

1. authorize the authenticated principal for the session;
2. enforce the existing evidence-submit rate limit once for the request;
3. reject missing/empty frame lists with HTTP `422`;
4. reject a list longer than the configured bound with HTTP `422` before any
   frame is read or stored;
5. read and validate each frame independently, in list order;
6. enforce the existing maximum byte size and non-empty checks for every frame;
7. pass every frame through the existing server-side media verification path;
8. persist each validated frame through `EvidenceService.add()` as
   `EvidenceType.LIVENESS`;
9. use a deterministic per-frame idempotency key derived from the supplied
   request key and zero-based frame index, such as
   `"<client-key>:frame:<index>"`;
10. emit one existing `EVIDENCE_UPLOADED` audit event per persisted frame,
    with the demo-qualified liveness action/metadata and no raw media;
11. return the existing response envelope for the final frame.

The helper must not call `LivenessProvider.assess()`. Capture and processing
remain separate lifecycle phases, and the current workflow has no liveness
result processor or multi-source result lineage contract. This is an explicit
scope boundary, not an omission.

## 5. Idempotency and partial failure

A request with an `Idempotency-Key` maps to one deterministic key per frame
index. A replay with identical bytes converges on the existing frame rows.
Reusing a frame key with materially different bytes raises the existing
`IdempotencyKeyReusedError` and maps to HTTP `409`.

Frame persistence is sequential. If a later frame fails after earlier frames
were stored, the existing service semantics apply: earlier accepted frames
remain durable and audited, while the failing frame is not represented as a
successful capture. The route must not claim an atomic batch transaction that
the current evidence/storage boundary does not provide.

A future atomic batch requirement would require a new governed persistence
abstraction and is outside this plan.

## 6. HTTP and failure mapping

The existing mappings remain in force:

- missing/empty multipart collection: `422`;
- frame count above configured maximum: `422`;
- empty frame: `400`;
- frame larger than `evidence_max_bytes`: `413`;
- unsupported or unrecognized media: `415`;
- missing session: `404`;
- inactive/expired session: `409`;
- materially different idempotency reuse: `409`;
- authorization failure: existing authentication/permission behavior;
- storage, database, audit, or provider/runtime failure: existing failure
  propagation and safe error handling, never a fabricated liveness failure.

No liveness outcome (`NO_FACE`, `AMBIGUOUS`, or `INSUFFICIENT_FRAMES`) is
created by the capture endpoint because no provider assessment occurs there.

## 7. Configuration

Add one settings value:

```text
liveness_max_frames: int = 5
```

The settings validator must reject values below `1` and values above the
small fixed demo ceiling selected by the project configuration policy. The
route reads the setting from `request.app.state.settings`, matching the
existing `evidence_max_bytes` access pattern.

The bound is configuration, not a client-controlled field and not a hidden
constant inside the router.

## 8. Validation gate

Focused validation must run in this order:

1. router unit tests for zero, one, two, five, and six files;
2. per-frame empty, oversized, unsupported, and malformed-media tests;
3. order-preserving persistence test;
4. idempotent replay and materially different reuse tests;
5. inactive, missing, and cross-tenant session tests;
6. real evidence integration test proving all accepted frames appear in
   `GET /{session_id}/evidence`;
7. Ruff;
8. strict mypy;
9. full pytest suite twice;
10. `git diff --check`, exact diff review, and status review.

Hostile validation must additionally cover a malformed frame after valid
frames, storage failure after an earlier successful frame, audit failure,
replayed multipart submissions, oversized frame lists, duplicate frame
content, frame order manipulation, and sensitive-data leakage through audit
metadata or error responses.

## 9. Explicit non-goals

This slice does not:

- invoke or modify `LivenessProvider`;
- create `LIVENESS_ASSESSMENT` results;
- alter `BiometricProcessor` or `/submit`;
- alter Decision Engine policy semantics;
- introduce video decoding, ffmpeg, OpenCV capture protocols, or queues;
- change `/document`, `/selfie`, or evidence retrieval contracts;
- make production presentation-attack-detection claims;
- resolve NIN/NIMC/BVN provider questions;
- begin Slice L frontend work.

## 10. Freeze statement

`BD-001.14` freezes Slice J as a bounded, multi-file **capture** extension
implemented through the existing single-evidence lifecycle. It intentionally
keeps capture persistence separate from liveness assessment because the
current result provenance model has no multi-frame batch identity and the
frozen Slice J boundary does not authorize inventing one.

Implementation may begin against this plan. Any change to batch atomicity,
assessment timing, result lineage, or liveness-provider integration requires
a new discovery/reconciliation record rather than an untracked expansion of
Slice J.
