# BD-001.21 — Slice M: End-to-End Integration (Discovery, Validation, Closure)

**Status:** CLOSED — documentation-only. No new architecture, no new code. This
record exists because Slice M was never given its own discovery/closure pass
when it was, in fact, already satisfied by Slice I's own mandatory gate test.
That gap in the paper trail — not a gap in the implementation — is what this
record closes.

**Combined into one record, not split into discovery/plan/closure**, per
explicit instruction: Slice M requires no new implementation plan because
there is nothing left to implement. What follows is discovery (what the
master plan actually requires), validation (proof against current code), and
closure (an honest statement of what is and is not established), in one
document.

---

## 1. Discovery — what Slice M requires

`BD-001` (the master plan) defines Slice M as:

> Full path: document capture → document processing (existing) → face
> extraction from document (Slice G) → reference embedding (B/C/D) → selfie
> capture → probe embedding (B/C/D) → liveness (F, if enabled) →
> `FaceMatch` (E) → Decision Engine (existing, zero change per BP-001
> §3/§4/Decision 11).

Note the master plan's own qualifier: **"liveness (F, if enabled)."** The
plan never assumed liveness assessment would necessarily be active. Whether
it is active today is a fact to check, not an assumption to carry forward —
see §3 below.

## 2. Validation — proof against current code, not inference

The chain above (minus liveness) is proven end to end by one test, added
during Slice I and never revisited since:

`tests/integration/test_verification_workflow.py::test_submit_delivers_biometric_evidence_into_a_verified_decision`

This test, against real Postgres and MinIO:

1. activates a policy requiring `FACE_MATCH` (`status == PASS → VERIFIED`);
2. uploads a real `DOCUMENT` capture that `SqlAlchemyDocumentProcessor`
   (using the project's existing `Deterministic*` fakes) turns into a real,
   effective `DOCUMENT_FIELD_EXTRACTION` row;
3. uploads a real `SELFIE` capture;
4. constructs a real `BiometricProcessor` wired with fixed capability
   doubles and a resolver that reads the actual `DOCUMENT_FIELD_EXTRACTION`
   row's id at call time (not a hardcoded id) — proving the resolver
   contract, not merely a canned response;
5. calls `VerificationWorkflowService.submit()` — the real, unmodified
   public entry point, not a direct call to `BiometricProcessor.process()`;
6. asserts `decision.outcome is VERIFIED`, the exact reason code, and a
   real, persisted `FACE_MATCH` row with `status=PASS` and correct
   `reference_evidence_result_id`/`probe_evidence_result_id`.

This is the one test in the codebase that proves `BiometricProcessor` and
the Decision Engine are actually wired together through the real workflow —
distinct from `test_biometric_processor.py` (which always calls
`process()` directly, never through `submit()`) and from
`test_decision_orchestration.py` (which seeds `FACE_MATCH` rows directly,
never through `BiometricProcessor`). Re-run fresh for this record:

| Check | Result |
|---|---|
| `tests/unit` | 485 passed |
| `tests/integration` + `tests/contracts` + `tests/security` | 308 passed |
| Ruff (full repo) | Clean |
| `mypy --strict` (`core`, `infrastructure`, `apps`) | Clean, 184 source files |

(These two suite groupings are run separately, not combined, for a reason
recorded in `BD-001.22` §4 — combining them currently trips an unrelated
test-harness issue, not a Slice M/N defect.)

## 3. Scope confirmation — what this record does and does not claim

**Established:**
- The full chain `submit() → DocumentProcessor → BiometricProcessor →
  FACE_MATCH → DecisionOrchestrator → persisted VERIFIED decision` is real,
  tested against real Postgres/MinIO, and has been since Slice I.
- `BiometricProcessor`'s own capability dependencies
  (`FaceDetector`/`FaceQualityAssessor`/`FaceEmbedder`/`FaceMatcher`) are
  each separately proven against the real InsightFace/ONNX Runtime adapters
  in their own unit tests (`test_insightface_detector.py`,
  `test_insightface_embedder.py`, etc.) — real models, small inputs, in
  isolation.

**Not established, and not claimed by this record:**
- **No single test runs the real InsightFace models through the real
  workflow end to end.** The mandatory gate test (§2) proves orchestration
  correctness using fixed capability doubles, per `BD-001.11`'s own frozen
  fixture strategy ("does the real application workflow correctly
  transport biometric evidence into the Decision Engine?", not "does
  InsightFace actually recognize two faces?"). Combining live models with
  the full live workflow in one test was never attempted and is not implied
  by anything in Slices G–L.
- **Liveness is not part of this chain.** Confirmed directly against
  `infrastructure/face/processor.py`: `BiometricProcessor.__init__` has no
  `liveness_assessor` parameter at all — a stricter omission than the
  master plan's own Slice G.2 sketch, which specified
  `liveness_assessor: LivenessAssessor | None` with `None` meaning "demo
  liveness disabled" as a sanctioned state. The implementation dropped the
  parameter entirely rather than keeping it as an accepted `None`. This is
  consistent with, not contradicted by, `BD-001.16` §2.5 ("Slice J captures
  frames but does not invoke this provider; Slice K must preserve that
  boundary") and `BD-001.18` §3.3/§6 ("`temporal_liveness_demo` remains
  inactive... Temporal Liveness Demo provider activation" listed under
  Slice K's explicitly deferred scope). Three separate slices, in sequence,
  independently confirmed the same boundary. This record confirms it a
  fourth time and treats it as settled, not newly discovered.
- **Real-backend browser validation is separate and not part of Slice M.**
  Slice L's own browser hostile matrix runs against a mocked API; whether
  the dashboard drives an actually-running PaxLI backend has not been
  tested and is tracked under Slice L's own closure, not here.

## 4. Closure statement

Slice M is **CLOSED**. The chain the master plan specifies is real and
proven against real infrastructure, exactly as far as the master plan's own
"if enabled" qualifier requires — no further than that, and no claim beyond
it.
