# BD-001.13 - Slice J Demo API Discovery

**Status:** DISCOVERY COMPLETE - implementation planning authorized

**Purpose:** reconcile the frozen Slice J demo API boundary against the
current FastAPI capture routes, liveness provider contract, evidence service,
and persisted liveness schema.

This record introduces no new architecture and does not reopen BD-001,
Slice F, or the closed biometric pipeline through Slice I.

## 1. Governing boundary

Slice J is the demo capture/API boundary only:

- retain `/document`;
- retain `/selfie`;
- retain `/submit`;
- retain `GET /{session_id}/evidence`;
- extend `/liveness` from one upload to a bounded multipart frame collection.

The required request shape is:

```text
frames: list[UploadFile]
```

The demo must use the frozen terminology **Temporal Liveness Demo** or
**Liveness Heuristic Demo**. It must not present the capability as production
liveness or production presentation-attack detection.

No change is authorized here to `BiometricProcessor`, `FaceMatcher`, the
Decision Engine, reference acquisition, provider architecture, workflow
ordering, or NIN/NIMC/BVN integration.

## 2. Current implementation facts

### 2.1 Current `/liveness` route

`apps/api/paxli_api/routers/evidence.py` currently declares:

```python
file: Annotated[UploadFile, File(...)]
```

It delegates to the shared `store_upload()` helper with
`EvidenceType.LIVENESS`. The route currently reads one file, enforces the
existing per-file byte limit, validates the actual media bytes through
`EvidenceService.add()`, stores one evidence object, and emits the existing
upload audit event.

`/document` and `/selfie` use the same helper and remain unchanged by Slice J.

### 2.2 Provider contract

`core/liveness/provider.py` already defines:

```python
async def assess(self, frames: list[bytes]) -> LivenessEvidence
```

The provider checks frame count before frame content. Fewer than two frames
produce `INSUFFICIENT_FRAMES`; otherwise frames are scanned in submission
order and the first unreadable, no-face, or ambiguous frame determines the
negative outcome. A valid sequence produces the temporal heuristic result.

The provider contract therefore already matches the frozen API direction. The
router is the missing producer of the frame list.

### 2.3 Evidence persistence

`EvidenceService.add()` accepts one byte payload per call and persists one
`Evidence` row/object per call. It already provides:

- tenant/session authorization through the session service;
- active-session enforcement;
- server-computed checksum and media verification;
- byte-size enforcement;
- encrypted object storage through the configured storage abstraction;
- idempotency handling;
- audit ordering for each persisted upload.

The current evidence model has no batch or sequence identifier for multiple
liveness frames. Slice J must therefore make an explicit implementation choice
about whether the batch is persisted as multiple liveness evidence rows or as
one serialized object. The frozen provider contract does not itself decide
that persistence representation.

### 2.4 Liveness result schema

`core/evidence_result/schemas.py` already defines
`LivenessAssessmentResult` with:

```text
live_score: float
attack_score: float | None
```

`EvidenceResultType.LIVENESS_ASSESSMENT` is already registered and classified.
The schema is compatible with the existing `LivenessEvidence` contract; no
schema change is indicated by this discovery.

## 3. Reconciliation questions for implementation planning

The following are implementation questions, not unresolved architecture:

1. **Frame bound:** choose and enforce the frozen demo default of five frames,
   with the bound represented in one configuration/constant location.
2. **Cardinality:** define explicit API behavior for zero, one, two-through-N,
   and greater-than-N files. Zero and one must reach the provider's
   `INSUFFICIENT_FRAMES` semantics only if the API accepts them; empty
   multipart input may instead be rejected as an HTTP request error. The
   implementation plan must choose and test one behavior explicitly.
3. **Per-frame validation:** every accepted frame must pass the existing
   byte-size, non-empty, and actual-media validation before liveness assessment
   receives the batch. No raw upload object or client MIME declaration may be
   trusted.
4. **Persistence representation:** determine whether each frame is stored as
   its own `EvidenceType.LIVENESS` capture or whether one batch object is
   required. The choice must preserve tenant isolation, idempotency, retention,
   deletion, auditability, and deterministic ordering.
5. **Assessment timing:** determine whether `/liveness` only captures frames or
   also invokes the provider and persists `LIVENESS_ASSESSMENT`. The frozen
   Slice J boundary and existing provider contract suggest capture should
   remain separate from `/submit` processing, but the implementation plan must
   ground this against the current workflow and evidence-result orchestration.
6. **Failure mapping:** provider unavailability, malformed media, insufficient
   frames, no-face, and ambiguous-frame outcomes must remain distinguishable.
   Provider/runtime failure must not become a subject liveness failure.
7. **Terminology:** route metadata, response descriptions, audit action names,
   tests, and future frontend copy must retain the demo qualification.

## 4. Required hostile-validation matrix

The implementation plan must include tests for:

- zero files;
- one file;
- exactly two files;
- exactly five files;
- six files rejected by the configured bound;
- an empty frame;
- an oversized frame;
- an unsupported or malformed frame among otherwise valid frames;
- frame order preservation;
- provider failure propagation/mapping;
- duplicate or replayed batch submission with idempotency behavior;
- inactive, expired, missing, and cross-tenant sessions;
- audit behavior when one frame or the batch fails;
- evidence listing after capture;
- `/submit` behavior consuming the resulting evidence through the existing
  workflow without changing workflow ordering.

## 5. Findings

- The frozen Slice J protocol decision remains implementable as written.
- No new provider, model, database table, Decision Engine behavior, or
  biometric architecture is required merely to accept the frame batch.
- The current shared single-file upload helper cannot be reused unchanged for
  a multi-file batch; it may be refactored or supplemented, but existing
  document/selfie behavior must remain unchanged.
- The provider and persisted liveness result schema already agree on the
  conceptual input/output shape.
- Provider research for NIN/NIMC/BVN does not block Slice J and remains outside
  this boundary.

## 6. Decision and next step

**Decision:** Slice J discovery is complete. The frozen bounded multipart
capture boundary is confirmed against the current code. No architectural
reconciliation is required.

**Next step:** write `BD-001.14` as the Slice J implementation plan, resolving
the explicitly listed persistence, cardinality, configuration, and failure
mapping details before changing the router.

No production code is changed by this record.
