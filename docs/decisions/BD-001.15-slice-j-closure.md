## 2. Implemented boundary

The `/liveness` route now accepts a bounded multipart collection:

```text
frames: list[UploadFile]
```

The accepted range is one through five frames. Each frame is persisted
independently as `EvidenceType.LIVENESS` through the existing evidence
lifecycle. The route does not invoke `LivenessProvider`, create
`LIVENESS_ASSESSMENT` results, modify `/submit`, or alter workflow ordering.

The existing `/document`, `/selfie`, `/submit`, and evidence-listing behavior
remain outside the Slice J implementation change.

Per-frame idempotency keys are derived from the client key and zero-based frame
index. The endpoint returns the existing evidence response shape for the last
frame, while all captures remain discoverable through evidence listing.

## 3. Hostile-validation findings

The focused API contract suite proves:

- zero frames -> HTTP 422;
- one frame -> HTTP 201;
- two frames -> HTTP 201;
- five frames -> HTTP 201;
- six frames -> HTTP 422 before frame persistence;
- accepted frames appear independently in evidence listing;
- same batch and idempotency key replay to the same frame evidence;
- changed bytes under the same frame key return HTTP 409;
- frame 2 persistence failure leaves frame 1 persisted, stops before frame 3,
  and returns an error rather than a batch-success response;
- required audit failure returns HTTP 500 after the existing evidence-before-
  audit persistence order has occurred.

The audit-failure behavior is recorded as observed inherited behavior from the
single-file evidence route. This closure does not silently change audit
ordering; any requirement to make capture and required audit atomic requires a
new governed discovery decision.

## 5. Security and data-protection confirmation

Authorization and evidence-submit rate limiting occur before frame-cardinality
rejection and before frame persistence. Each frame uses the existing server-
side media validation, tenant/session scoping, encryption, retention,
deletion, and audit path. Audit metadata contains evidence type and size only;
raw frame bytes are not included.

The six-frame rejection happens before the per-frame persistence loop, so an
oversized batch cannot partially store its prefix. A failure during a valid
batch remains non-atomic by design: already accepted frames remain durable,
and later frames are not attempted after the failure.

The implementation makes no production presentation-attack-detection claim.
The capability remains the explicitly labeled Temporal Liveness Demo / Liveness
Heuristic Demo.

## 6. Explicitly deferred scope

- invoking `LivenessProvider` from an API or workflow processor;
- persisting `LIVENESS_ASSESSMENT` from the capture endpoint;
- introducing a batch evidence entity or atomic multi-frame transaction;
- changing evidence-before-audit ordering;
- changing `/submit`, `BiometricProcessor`, or Decision Engine semantics;
- NIN/NIMC/BVN provider integration;
- frontend capture work;
- production liveness or presentation-attack detection.

## 7. Final closure statement

Slice J is **CLOSED**. The demo can now capture one through five liveness
frames through the real API and existing evidence lifecycle without activating
assessment or changing verification decisioning.

Further changes to frame batching, liveness result lineage, atomicity, or audit
ordering require a new discovery/reconciliation record rather than an
untracked expansion of Slice J.
