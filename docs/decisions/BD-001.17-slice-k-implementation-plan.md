# BD-001.17 - Slice K Structured Observability Implementation Plan

**Status:** FROZEN - implementation authorized

**Purpose:** translates `BD-001.16`'s discovery into an exact, bounded
structured stage-event layer over the existing structlog JSON and sanitizer
infrastructure.

No architectural decisions are introduced here. This plan does not reopen
Slices G, G.2, H, I, or J, the Decision Engine, evidence semantics, workflow
ordering, or provider integrations.

## 1. Core invariant

Structured observability observes execution. It never becomes part of
verification processing, evidence semantics, audit durability, or decision
logic.

A logging failure MUST NOT alter evidence, verification, or decision state:

```text
processor operation
      -> attempt structured log
      -> log succeeds: continue or re-raise original operation result
      -> log fails: suppress/fallback, preserve original operation result
```

A logger exception must never replace the original provider, processor,
storage, database, or Decision Engine exception.

## 2. Bounded event vocabulary

Add one small operational event vocabulary, emitted through the existing
sanitized structlog configuration:

```text
verification_stage_started
verification_stage_completed
verification_stage_inconclusive
verification_stage_unavailable
verification_stage_failed
```

The controlled `stage` field identifies the operation. No processor or
provider may invent a new event name for an ordinary stage transition.

The initial controlled stage values are:

```text
document_quality
document_classification
document_mrz
document_barcode
document_ocr
document_field_extraction
reference_acquisition
face_detection_reference
face_quality_reference
face_embedding_reference
face_detection_probe
face_quality_probe
face_embedding_probe
face_match
temporal_liveness_demo
liveness_capture
```

`liveness_capture` observes Slice J frame capture only. It must never imply
that `LivenessProvider.assess()` ran. `temporal_liveness_demo` is emitted only
where a future governed assessment integration actually invokes the provider;
Slice K itself must not activate that provider path.

## 3. Structured event fields

The event helper must accept only an explicit operational field allow-list:

```text
event
stage
outcome
duration_ms
attempt
request_id
correlation_id
session_id
evidence_result_id
model_id
model_version
failure_category
frame_count
```

Fields are omitted or set to `None` when unavailable. `tenant_id` is excluded
by default and must not be added globally through context binding in this
slice. Raw payloads, content, filenames where sensitive, provider response
objects, and arbitrary metadata dictionaries are not accepted by the helper.

`duration_ms` is rounded and bounded to operational precision. `attempt` is a
positive integer when retry context exists. `model_id` and `model_version`
are allowed only when they are stable model metadata, never model output or
input content.

The helper must use the existing structlog logger and therefore the existing
sanitizer/JSON renderer. It must not create a second logging configuration.

## 4. Emission location

Events are emitted by orchestration boundaries, not low-level adapters:

```text
DocumentProcessor
  -> stage event around each document stage

BiometricProcessor
  -> stage event around reference acquisition, face stages, and FaceMatch

Slice J API capture boundary
  -> liveness_capture event per accepted frame or bounded batch event

Temporal Liveness Demo provider
  -> no new invocation from Slice K
```

`InsightFaceDetector`, `InsightFaceEmbedder`, `InsightFaceLivenessProvider`,
PaddleOCR, OpenCV, and other vendor/runtime adapters must not independently
emit duplicate stage events. Provider internals remain operationally opaque
behind their owning orchestration stage.

The event helper must be best-effort and failure-isolated. The owning
processor catches logger failures only around the logging call, never around
the operation being observed. The original operation result or exception is
preserved exactly.

## 5. Outcome mapping

Use the existing domain semantics without changing them:

| Event | When |
|---|---|
| `verification_stage_started` | immediately before the owned operation |
| `verification_stage_completed` | operation returns a successful/usable result |
| `verification_stage_inconclusive` | operation returns a valid non-terminal observation or inconclusive evidence |
| `verification_stage_unavailable` | known provider/runtime unavailability or retryable dependency condition |
| `verification_stage_failed` | unexpected exception or non-classified failure |

Logging classification must not rewrite evidence status or final decision
outcome. In particular, `UNAVAILABLE` remains operational/provider state and
must not become a rejection; `INCONCLUSIVE` remains domain evidence semantics.

For persisted stages, `evidence_result_id` may be logged after persistence.
The log does not replace the EvidenceResult or audit row.

## 6. Context policy

Do not add implicit tenant context in this slice. Pass request ID,
correlation ID, and session ID explicitly where the owning method already has
them. Do not introduce global context variables unless an implementation
review proves they are needed and records their lifecycle/cleanup semantics.

The minimum useful correlation fields are:

```text
request_id
correlation_id
session_id
stage
attempt
```

A missing context value is represented as `None`, not an invented identifier.

## 7. Retry and concurrency behavior

Each actual orchestration-stage attempt may emit a started and terminal event.
The event fields must distinguish attempts when retry context exists. Logging
must not deduplicate, supersede, or mutate EvidenceResult rows.

Concurrent processing may produce concurrent operational events. That is
acceptable; correctness comes from the existing idempotent evidence and
workflow persistence mechanisms. The logger must not introduce locks or
shared mutable state that change concurrency behavior.

## 8. Slice J boundary

Slice K may observe accepted liveness captures with `stage=liveness_capture`
and fields such as frame count and session/request context. It must not call
the liveness provider as a side effect of capture logging:

```text
/liveness capture -> liveness_capture event
/liveness capture != Temporal Liveness Demo assessment
```

No `LIVENESS_ASSESSMENT` result is created by Slice K.

## 9. Security validation

Hostile tests must inspect rendered JSON output, not only the Python event
mapping. Use unmistakable canaries such as:

```text
OCR_CANARY_9f...
NIN_CANARY_...
BVN_CANARY_...
EMBEDDING_CANARY_...
LIVENESS_FRAME_CANARY_...
```

The tests must prove that these values do not appear in rendered logs when
passed through representative stage logging paths. Also test raw bytes,
embedding arrays, nested provider responses, exception text, and arbitrary
metadata fields.

Test that logger failure does not mask:

- a processor exception;
- a provider unavailable exception;
- an evidence persistence exception;
- a workflow/Decision Engine exception.

Test that required audit behavior remains durable independently of logs.

## 10. Implementation boundary

The plan authorizes the smallest coherent implementation surface:

| File/area | Planned change |
|---|---|
| `infrastructure/observability/logging.py` or adjacent helper | bounded stage-event helper with logging-failure isolation |
| document orchestration owner | stage events around document stages |
| biometric orchestration owner | stage events around reference, face, and match stages |
| Slice J API capture owner | capture observability only, without assessment activation |
| focused observability tests | rendered JSON, canary leakage, failure isolation, context, and vocabulary |

No changes are planned under `core/decision/`, policy semantics, evidence
schemas, audit persistence, provider internals, or deferred identity-provider
integration.

The exact final file list must be reconciled against actual call sites before
staging, as in prior slices. Unrelated workspace changes remain outside the
implementation commit.

## 11. Validation gate

Run in this order:

1. focused event-helper and sanitizer tests;
2. focused document and biometric stage-event tests;
3. Slice J capture observability tests, proving no provider invocation;
4. hostile rendered-JSON canary tests;
5. logger-failure isolation tests;
6. Ruff;
7. strict mypy;
8. full pytest suite twice;
9. `git diff --check`;
10. exact diff/name/status review;
11. selective staging review;
12. implementation commit only after explicit boundary confirmation.

The closure record will remain a separate documentation commit.

## 12. Freeze statement

`BD-001.17` freezes Slice K as a bounded structured stage-observability layer
using the existing structlog JSON and sanitizer infrastructure. It observes
orchestration without changing processing, evidence, audit, policy, or
Decision Engine semantics.

Implementation may begin against this plan. Any request to add provider-level
logging, tenant-wide implicit context, payload-bearing logs, new audit
semantics, or liveness assessment activation requires a new discovery or
reconciliation record.
