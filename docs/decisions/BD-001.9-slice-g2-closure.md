## 3. Implemented scope

### 3.1 BiometricProcessor

Introduced:

`infrastructure/face/processor.py`

`BiometricProcessor` now provides the frozen sequential orchestration boundary:

```text
Reference chain
      ↓
Probe chain
      ↓
FaceMatch evaluation
```

Invocation is unconditional at the top level, while work within each chain remains conditional on its own acquisition and evidence state.

Exceptions propagate from a failed stage and prevent subsequent stages in the same invocation from executing.

Workflow-level retry remains the recovery boundary.

### 3.2 Reference-side processing

Implemented:

```text
ReferenceIdentity
      ↓
FACE_DETECTION_REFERENCE
      ↓
FACE_QUALITY_REFERENCE
      ↓
FACE_EMBEDDING_REFERENCE
```

Reference acquisition is invoked on every processor call.

The implementation preserves the frozen G.2-S11 semantics:

* `NOT_AVAILABLE` → silent no-op
* `NO_FACE_FOUND` → `FACE_DETECTION_REFERENCE` `INCONCLUSIVE`
* `AMBIGUOUS` → `FACE_DETECTION_REFERENCE` `INCONCLUSIVE`
* no synthetic downstream quality or embedding evidence is created when acquisition terminates early

Quality does not gate embedding, consistent with the frozen Slice C decision.

The demo's `ReferenceArtifactEmbedding` variant remains explicitly unsupported (raises `NotImplementedError`, per `BP-001` §6c's own still-OPEN status).

### 3.3 Probe-side processing

Implemented:

```text
SELFIE
  ↓
FACE_DETECTION_PROBE
  ↓
FACE_QUALITY_PROBE
  ↓
FACE_EMBEDDING_PROBE
```

SELFIE cardinality follows the frozen rules:

* zero effective captures → silent no-op
* one effective capture → normal probe processing
* multiple effective captures → ambiguous; all three probe stages receive `INCONCLUSIVE` evidence with `AMBIGUOUS_SELFIE_CAPTURE`; no capture is selected and no FaceMatch is attempted

### 3.4 FaceMatch orchestration

FaceMatch processing performs a fresh persistence read of the current effective reference and probe chains immediately before comparison.

A persisted embedding is considered usable only when:

1. the embedding is effective;
2. its status is `PASS`;
3. its parent is the current effective quality result;
4. that quality result's parent is the current effective detection result;
5. the current detection result is `PASS`.

Therefore:

> An effective `PASS` embedding is not necessarily a current usable embedding.

This complete lineage check (`_lineage_is_current`) prevents an orphaned embedding from an earlier reference or probe lineage from being used for FaceMatch.

When both current embeddings are usable:

* compatible representations → `FACE_MATCH` `PASS`
* incompatible representations → `FACE_MATCH` `INCONCLUSIVE` with `REPRESENTATION_INCOMPATIBLE`
* no threshold is applied by `FaceMatcher`

FaceMatch freshness is determined by exact parent equality:

```text
FACE_MATCH.parents ==
(
    current_reference_embedding.id,
    current_probe_embedding.id,
)
```

### 3.5 Stale FaceMatch invalidation

An existing stale FaceMatch is invalidated through the existing `EvidenceResultService.supersede()` path.

When current parent evidence is not usable:

```text
FACE_MATCH
    ↓ supersede
INCONCLUSIVE
PARENT_EVIDENCE_NOT_USABLE
result=None
```

The invalidation records the currently usable embedding parent IDs, if any, preserving partial lineage information without fabricating a comparison.

No new persistence primitive, table, status, or Decision Engine mechanism was introduced.

## 4. Implementation findings

Two significant findings occurred during the implementation/validation cycle.

### 4.1 Finding A — stale reference lineage consistency gap

**Detection point:** plan/discovery review, before implementation.

The initial `BD-001.8` draft defined FaceMatch eligibility as simply:

```text
effective embedding + PASS
```

Review against the frozen G.2-S11 behavior revealed a real inconsistency.

G.2-S11 intentionally allows reference acquisition to terminate at:

```text
FACE_DETECTION_REFERENCE
```

without creating replacement quality or embedding rows.

Consequently, older:

```text
FACE_QUALITY_REFERENCE
FACE_EMBEDDING_REFERENCE
```

rows could remain physically present and effective even after their upstream reference lineage became stale.

A shallow `effective + PASS` check on the old embedding would therefore have allowed stale biometric evidence to participate in FaceMatch.

#### Resolution

The implementation plan was corrected before implementation.

FaceMatch eligibility was changed to require complete current lineage:

```text
current detection
      ↓ exact parent
current quality
      ↓ exact parent
current embedding
```

The final implementation performs this check independently using fresh database state.

This was a **plan-level consistency correction**, not an architectural reopening.

The frozen G.2-S11 decision remains unchanged: downstream rows are not synthetically created or proactively cleaned up when reference acquisition terminates early.

The critical integration regression test:

`test_stale_reference_lineage_excludes_orphaned_embedding_and_invalidates_match`

explicitly validates this behavior against real persistence.

### 4.2 Finding B — `Evidence.id` vs `EvidenceResult.id`

**Detection point:** real integration testing against Postgres.

The initial implementation of the probe detection stage used:

```text
parent_evidence_result_ids=(capture.id,)
```

The defect was that `capture.id` is an ID belonging to the raw `Evidence` capture table, while `parent_evidence_result_ids` is exclusively an ID space belonging to `EvidenceResult`.

These are distinct persistence entities and distinct ID spaces.

The existing EvidenceResult provenance validation correctly rejected the mismatch.

#### Resolution

The probe detection stage was corrected to preserve the established distinction used by `DocumentProcessor`:

```text
SELFIE Evidence
      │
      └── source_reference
              ↓
FACE_DETECTION_PROBE EvidenceResult
```

Subsequent derived stages retain genuine EvidenceResult lineage:

```text
FACE_DETECTION_PROBE.id
        ↓
FACE_QUALITY_PROBE.parent_evidence_result_ids

FACE_QUALITY_PROBE.id
        ↓
FACE_EMBEDDING_PROBE.parent_evidence_result_ids
```

The reference side needed no equivalent change: it has no raw `Evidence` capture to cite at all (`ReferenceIdentity.reference_artifact`'s bytes are transient, never a stored `Evidence` row), so `identity_claim` was, and remains, correctly carried via `parent_evidence_result_ids` alone.

The correction introduced no architectural scope expansion and follows the existing repository convention.

This defect was specifically valuable because it was caught by execution against real Postgres rather than static inspection alone.

## 7. Security and evidence integrity

Slice G.2 introduces no new raw biometric persistence mechanism.

Biometric evidence remains subject to the existing EvidenceResult sensitivity and encryption mechanisms.

The processor:

* preserves tenant-scoped queries;
* does not log raw biometric images;
* does not fabricate embeddings or comparisons;
* does not use incompatible embeddings;
* does not silently select among multiple SELFIE captures;
* does not infer FaceMatch success from similarity alone;
* preserves parent evidence-result lineage;
* invalidates stale derived FaceMatch evidence rather than retaining it as current.

The `Evidence.id` / `EvidenceResult.id` defect also reinforces the importance of maintaining the repository's distinction between source capture references and derived-evidence lineage.
