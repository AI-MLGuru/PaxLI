## 1. Scope and governing decisions

Slice H replaces the three undifferentiated `FACE_DETECTION`/
`FACE_QUALITY`/`FACE_EMBEDDING` `EvidenceResultType` members with six
role-qualified ones, and completes `BP-001.5` Decision 20's

  live data affected (nothing had ever persisted a row of the three
  original members).
- **`BD-001.4` H.2:** `FaceMatchResult` gains
  `reference_evidence_result_id`/`probe_evidence_result_id` and all
  three frozen invariants (distinctness; reference and probe each
  present in the envelope's own `parent_evidence_result_ids`).
- **`BD-001.5` §5 (corrected during its own review):** distinctness is
  enforced inside `FaceMatchResult.model_validator`; the two
  parent-membership invariants are enforced inside
  `validate_result_payload()`, called from `EvidenceResultService.create()`/
  `.supersede()` — the one point both the payload and the envelope's
  parent set are already in scope together. `BiometricProcessor`
  (Slice G.2) consumes an already-complete contract; it was never
  designated this contract's enforcement boundary, and no code in this
  slice makes it one.

## 5. Implementation finding, recorded explicitly, not hidden

During implementation, completion of the H.2 `FaceMatchResult`
contract revealed additional test consumers beyond the taxonomy-rename
blast-radius estimate `BD-001.5` §8 enumerated. These were compatibility
updates required because `reference_evidence_result_id`/
`probe_evidence_result_id` became mandatory payload fields — every
existing test constructing a `FACE_MATCH` result payload through
`EvidenceResultService.create()`/`.supersede()` needed updating, not
only the ten call sites §8 identified for the H.1 rename itself.

Investigating this surfaced a real risk in a purely mechanical fix:
most of the newly-found consumers (in `test_evidence_result_service.py`,
`test_evidence_result_persistence.py`, `test_decision_persistence.py`)
were generic service/persistence tests with no real dependency on
`FACE_MATCH` specifically, and were moved to `DOCUMENT_QUALITY`
(sharing `FACE_MATCH`'s own `SENSITIVE` classification tier, so the
substitution changes nothing about what each test actually proves).
Two consumers demonstrated genuine semantic dependence on `FACE_MATCH`
and were corrected deliberately instead:
`test_full_pipeline_verified_outcome_against_real_infrastructure`
(`test_decision_orchestration.py`) exercises a real policy rule that
specifically requires `FACE_MATCH` evidence with `status == PASS` — a
mechanical rename would have silently broken the test's own meaning
(it would still pass syntactically but stop testing what it claims to);
`test_decision_survives_hard_deletion_of_the_evidence_it_referenced`
(`test_decision_persistence.py`) carried a literal `"FACE_MATCH"`
string assertion on a value that, after an earlier attempted swap to
`DOCUMENT_QUALITY`, needed updating to match — caught by running the
tests, not by inspection alone.

This is recorded as a positive engineering finding, not merely a
caveat: it demonstrates that implementation surfaced a distinction
static planning could not fully enumerate in advance (which existing
consumers merely borrow an evidence type as an arbitrary fixture,
versus which ones depend on it semantically), and that the distinction
was resolved by actually running the affected tests and reading each
failure, rather than by assuming a grep-based rename was safe. No
production scope expansion resulted — every file this finding touched
is a test file; the production boundary stayed exactly the four files
`BD-001.5` §11 named.

## 7. Security / sensitivity confirmation

No classification tier changed for any evidence type in this slice —
each role-qualified member inherits its original pair's tier exactly
(`FACE_DETECTION_*`/`FACE_QUALITY_*` stay `SENSITIVE`,
`FACE_EMBEDDING_*` stays `HIGHLY_SENSITIVE`), confirmed via the
reviewed `classification.py` diff. No new persisted field carries
biometric content: `reference_evidence_result_id`/
`probe_evidence_result_id` are UUIDs (references to other rows), never
embeddings, images, or scores themselves. The new provenance check
(`_validate_face_match_provenance`) operates only on UUID comparisons
already present in the validated payload and the caller-supplied
parent tuple — no new code path touches raw biometric content, and no
`logger`/`print` call was added anywhere in this commit (confirmed by
direct inspection of the diff).
